Programming Guideline & Commenting

Difficulty: Beginner | Category: C# Introduction

Mental Model

Code is read up to 10 times more often than it is written. Programming guidelines—such as naming conventions, strict class structures, and disciplined commenting—are not bureaucratic rules; they are a communication protocol between engineers. Proper formatting transforms a raw logic script into a maintainable engineering asset.

A. Why Does This Exist?

Due to time restrictions, lazy programming, or enthusiasm for immediate results, commenting and code formatting often take a back seat. When a team works on a module over a long cycle, the lack of guidelines leads to architectural chaos. Standardized guidelines exist to decrease the cost of knowledge transfer between developers. They remove the mental overhead of parsing code structure, allowing developers to focus purely on business logic and architecture.

B. Official Naming & Structure Guidelines

In our architecture, we strictly adhere to the following naming conventions to ensure predictability across the entire codebase:

1. Capitalization Rules

  • PascalCase: Used for Classes, Methods, Properties, Events, and Namespaces.
    • Exceptions: Suffix with Exception, Attributes suffix with Attribute.
    • Interfaces: Prefix with a capital I (e.g., ICustomer).
    • Enums: Prefix with Enm (e.g., EnmEmployeeType).
  • camelCase: Used for Local Variables and Method Parameters. Avoid single characters (like x or y) except in for loops. Never enumerate variables (e.g., text1, text2).
  • _camelCase: Used strictly for Private Instance Fields (e.g., _databaseContext). Avoid public/protected fields entirely; use Properties instead.
  • Booleans: Prefix boolean variables/properties with can, is, or has (e.g., hasActiveSubscription).
  • Generics: Use a single capital letter, such as T or K (e.g., public class FifoStack<T>).

2. Mandatory Class Structure (Regions)

Every class must organize its members in the following exact order, wrapped in #region directives. This allows developers to instantly collapse and navigate massive files:

  1. #region Private Members
  2. #region Public Properties
  3. #region Constructors
  4. #region Public Methods
  5. #region Private Methods

C. Commenting Practices

Comments are for communicating information to future developers that is not obvious from reading the code.

1. Rules of Commenting

  • Use // or /// ONLY. Never use /* ... */ block comments.
  • No Flowerboxing or Art Projects: Do not draw ASCII boxes (e.g., // *********) around your comments. It creates a time-wasting maintenance task to keep the box symmetrical when text changes.
  • Module Headers: Leave a brief description at the top of complex files: Name of the module and its Purpose.
  • Comment While Coding: Do not wait until the program works to write comments. Leaving it for later takes a lot of work and context is lost. Time saved by not commenting during coding is lost twice-over when trying to reverse-engineer it later.
  • Avoid Obvious Comments: Well-written code is self-documenting.
    Bad: // get the country code
    Good: Rely on the variable name var countryCode = GetCountryCode();

2. XML Documentation (///)

Always apply C# XML comment blocks to public, protected, and internal declarations. Include <summary>, <param>, <return>, and <exception>. Method comments must include the purpose, calling context (e.g., Calling from GUI), and parameter descriptions.

D. Internal Working: XML Comments

When you type /// above a method, what happens internally?

When the Roslyn compiler builds your project, it strips these XML tags from the compiled Intermediate Language (IL) binary to save space. However, it extracts them into a companion .xml file (e.g., KnowledgeBase.Core.xml) that is deployed alongside your .dll. When another project references your DLL, Visual Studio reads that XML file and dynamically generates the hover-over IntelliSense tooltips. This means your comments directly power the IDE's UI for other developers.

Example 2: Exception Handling and Resource Management Guidelines

Our guidelines strictly mandate how to interact with the database and handle exceptions. Specifically: Database connections must use using, database calls must NEVER be nested inside loops, and exceptions must be re-thrown using throw;.

C# - Exception and Resource Example
public void BulkUpdateArticles(List<int> articleIds)
{
    // GUIDELINE: Use 'using' to ensure external resources are disposed immediately.
    // GUIDELINE: Never put database connections inside a loop (N+1 problem).
    using (var connection = new MySqlConnection("..."))
    {
        try
        {
            // Execute a single bulk query rather than looping over articleIds
            ExecuteBulkQuery(connection, articleIds);
        }
        catch (SqlException ex) // GUIDELINE: Catch most derived exception first
        {
            LogError(ex);
            throw; // GUIDELINE: 'throw;' preserves the call stack. 'throw ex;' destroys it.
        }
        catch (Exception ex)
        {
            LogError(ex);
            throw;
        }
        // GUIDELINE: No empty catch blocks. Do not use try/catch for flow control.
    }
}

Edge Cases, Failure Modes and What If...?

What if I use "throw ex;" instead of "throw;"?

Cause: A developer attempts to re-throw an exception to the caller but explicitly includes the exception variable: throw ex;

Behavior: The CLR resets the Stack Trace to the exact line where throw ex; was called. The original line of code that actually caused the error (deep inside the repository) is permanently erased from the error logs.

Solution: Always use throw; to preserve the original call stack.

What if I query the database inside a loop?

Scenario: Retrieving details for 1,000 articles by calling _db.GetArticleById() inside a foreach loop.

Behavior: This violates the "Nested Database Call" guideline. It opens and closes the connection 1,000 times, causing TCP Port Exhaustion and overwhelming the MySQL server with connection overhead, bringing down the entire production environment.

Solution: Construct a single query using WHERE id IN (...).

Production Engineering Perspective

In production environments, naming conventions and commenting are not left to trust. Production engineers enforce them automatically.

  • .editorconfig: Teams place an .editorconfig file in the root of the Solution. This file mathematically defines our exact casing rules (e.g., _camelCase for privates). If a developer violates it, Visual Studio highlights it as an error.
  • Static Analysis (SonarQube): Build servers analyze code for empty catch blocks or nested database calls, rejecting the Pull Request before it ever merges.
  • Code Reviews: As stated in the commenting guidelines, code must be handed to a fellow developer during a code review specifically to ask "how much do you understand?" based purely on the comments.

Final Mental Model

Think of your code as a user interface for the next developer who has to read it. Naming conventions are the layout, #region tags are the navigation menus, and XML comments are the tooltips. Adhering to these guidelines—especially regarding exception stack traces and resource disposal—ensures the application is scalable, debuggable, and safe for a massive team to maintain.
