10. Composite Index Prefixing (Deep Dive)

Performance & Indexing

Composite Indexes & Leftmost Prefixing

A Composite Index is a single physical B+Tree index built across multiple columns. In this section, "prefixing" strictly refers to the Leftmost Prefix behavior of the B+Tree structure, which dictates how the MySQL Optimizer uses the index.

Clarification

Do not confuse this with String Prefix Indexes (e.g., INDEX(title(20))). We are analyzing how multi-column indexes govern query execution paths based on column ordering.

The Physical Structure of the B+Tree

Assume we create the following composite index on the articles table:

CREATE INDEX idx_author_status_date ON articles (author_id, status, created_at);

Internally, InnoDB builds a single B+Tree. It sorts the entries strictly hierarchically:

  1. First, it sorts entirely by author_id.
  2. Only when the author_id is identical between two rows does it sort those specific rows by status.
  3. Only when both author_id and status are identical does it sort those rows by created_at.

Because of this physical hierarchy, the Optimizer can only use the index for Index Access / Search if your WHERE clause provides the columns from left to right without skipping.

Execution Path Analysis (Different Cases)

Let's deeply analyze how the Optimizer treats different queries against INDEX(author_id, status, created_at).

Case 1: Equality + Equality (Perfect Prefix)

SELECT * FROM articles WHERE author_id = 101 AND status = 'Published';

Execution: The Optimizer uses the first two columns of the index for Index Access. It navigates the B+Tree directly to author_id=101, and then within that subtree, navigates directly to status='Published'. The created_at column in the index is ignored for this query. (EXPLAIN shows ref access).

Case 2: Missing Leading Column (The Index Fails)

SELECT * FROM articles WHERE status = 'Published';

Execution: Because the B+Tree is sorted primarily by author_id, the status values are scattered throughout the entire tree. The Optimizer cannot use this index for direct access. It must perform a Full Table Scan (or an Index Scan if the index is covering). The index structure is practically useless for this query.

Case 3: Equality + Range (The Stopping Point)

SELECT * FROM articles 
WHERE author_id = 101 AND status > 'Draft' AND created_at = '2026-01-01';

Execution: This is a critical edge case. The Optimizer uses author_id for direct equality lookup. It then uses status > 'Draft' for range traversal within that author. However, because status is a range, the hierarchical sorting of the third column (created_at) is now broken across the multiple statuses fetched.

Therefore, the index stops being used for B+Tree searching after the status column. The created_at condition is evaluated as Additional Filtering (Index Condition Pushdown) as it scans the range, rather than an instant B+Tree dive.

Case 4: Skipped Middle Column

SELECT * FROM articles 
WHERE author_id = 101 AND created_at > '2026-01-01';

Execution: The Optimizer uses author_id to jump to the right section of the B+Tree. But because status was skipped, it cannot use created_at for the search (the dates are not sorted sequentially because the statuses are interleaved). It scans every row for author_id = 101 and applies the date filter post-access.

Index Access vs Additional Filtering

It is incorrect to say the Optimizer "ignores" later columns when the prefix is broken.

In Case 4 above, modern MySQL uses Index Condition Pushdown (ICP). Even though created_at cannot be used to instantly navigate the B+Tree, the Execution Engine still reads the created_at value from the Secondary Index leaf node. If the date doesn't match, it discards the row immediately. This saves the engine from doing a Double Lookup into the Clustered Index for a row it would eventually throw away. (EXPLAIN shows Using index condition).

Interview: What Happens Internally?

Reasoning Challenge

Scenario: You have INDEX(author_id, created_at).

Query A: SELECT * FROM articles WHERE author_id = 101 ORDER BY created_at;

Query B: SELECT * FROM articles WHERE author_id > 100 ORDER BY created_at;

Question: How does the internal sorting execution differ radically between Query A and Query B?

View the Internal Explanation

Query A: Because author_id is an equality condition (= 101), the B+Tree guarantees that all rows under author_id = 101 are already physically sorted by the second column, created_at. The Execution Engine just reads the index sequentially. No extra CPU sorting is required.

Query B: Because author_id is a range condition (> 100), the Execution Engine retrieves multiple authors (e.g., 101, 102, 103). While the dates are sorted within author 101, and sorted within author 102, the combined result set of all authors is not sorted globally by date. Therefore, the Optimizer is forced to allocate a Sort Buffer, fetch all the rows, and perform a physical QuickSort (a "filesort") on the result set before returning it.
