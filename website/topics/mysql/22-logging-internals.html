The Three Logs of MySQL

To understand MySQL crash recovery, replication, and transaction isolation, you must understand the exact physical boundaries between the Undo Log, Redo Log, and Binary Log. They are NOT interchangeable.

1. The Undo Log

Primary Purpose: Rollback & MVCC (Multi-Version Concurrency Control).

  • What it is: When you update or delete a row, InnoDB writes the previous version of the row into the Undo Log before modifying the page in the Buffer Pool.
  • Rollback: If you issue ROLLBACK, InnoDB reads the Undo Log and physically reverses the changes in the Buffer Pool.
  • MVCC: If Transaction B wants to read a row that Transaction A is currently modifying, InnoDB points Transaction B to the Undo Log so it can read the old, consistent version of the row.

2. The Redo Log

Primary Purpose: Crash Recovery & Durability (The 'D' in ACID).

  • What it is: Modifying physical 16KB data pages on disk for every query is too slow. InnoDB modifies the pages in memory (Buffer Pool) and writes a fast, sequential record of the change to the Redo Log.
  • Crash Recovery: If the server loses power, the modified pages in the Buffer Pool are lost. Upon restart, InnoDB reads the physical Redo Log, finds the changes that were never written to the .ibd files, and re-applies them.

3. The Binary Log (Binlog)

Primary Purpose: Replication & Point-In-Time Recovery.

  • What it is: A log maintained by the MySQL Server Layer (not InnoDB). It records committed transactions either as the literal SQL statements (Statement-Based) or the exact row modifications (Row-Based).
  • Replication: Replica servers connect to the Primary, download the Binlog, and execute the events to synchronize their data.
  • Why it doesn't replace the Redo Log: The Binlog records logical events at the server level upon commit. The Redo Log records physical byte-level page changes inside the InnoDB engine continuously. Crash recovery requires physical page reconstruction, which the Binlog cannot provide.

Reasoning Challenge

Question: Why can't we simply use the Binary Log for crash recovery and delete the Redo Log to save disk space?

View the Internal Explanation

The Binary Log and Redo Log operate at completely different levels of the MySQL architecture.

The Binary Log operates at the Server level and logs logical events (e.g., "Row 5 was updated to 'Active'") only when a transaction commits. If a server crashes mid-transaction, the uncommitted data isn't in the Binlog.

The Redo Log operates at the InnoDB Storage Engine level. It logs physical byte-level modifications to the 16KB data pages in the Buffer Pool. It is written to continuously, even for uncommitted transactions. When the server restarts after a crash, InnoDB must physically reconstruct torn or dirty data pages block-by-block. The logical Binlog does not contain the physical page offsets required to reconstruct a corrupted B+Tree.
