9. Indexing & Storage Engine Internals

Performance & Indexing

Indexing in InnoDB

At the SQL level, an index is just a rule you add to a column to "make queries faster". But at the InnoDB Storage Engine level, an index is a physical, hierarchical data structure written to disk (in 16KB pages) that completely dictates how your data is physically organized.

Clustered Index vs Secondary Index

This is the most critical distinction in InnoDB storage architecture.

The Clustered Index (The Primary Key)

In InnoDB, the table data is not stored in a random heap. The table data IS the Primary Key index. This structure is called the Clustered Index.

  • It is a B+Tree.
  • The non-leaf nodes contain the Primary Key values (to guide the search).
  • The leaf nodes contain the actual physical row data for every column.

The Secondary Index (Non-Primary Indexes)

If you create an index on the email column, InnoDB builds a separate B+Tree for email.

  • The non-leaf nodes contain the email values.
  • The leaf nodes DO NOT contain the row data. Instead, they contain the Primary Key value of that row.

The Execution Path: Double Lookup (Key Lookup)

What happens when you run this query?

SELECT first_name, last_name FROM users WHERE email = 'test@example.com';

Because the query filters by email (a Secondary Index), but requests first_name and last_name (which are not in the email index), the Execution Engine must perform a Double Lookup:

  1. It traverses the Secondary Index (email) B+Tree to find 'test@example.com'.
  2. It extracts the Primary Key value (e.g., id = 105) from the leaf node.
  3. It takes id = 105 and navigates down the Clustered Index B+Tree.
  4. It reaches the Clustered Index leaf node, retrieves the full row data, extracts first_name and last_name, and returns them.

Covering Indexes: Bypassing the Clustered Index

A "Covering Index" is not a special type of index; it is a state of execution where the query's requested columns are completely "covered" by the secondary index structure.

-- Query 1 (Requires double lookup)
SELECT id, email, first_name FROM users WHERE email = 'test@example.com';

-- Query 2 (Covering Index)
SELECT id, email FROM users WHERE email = 'test@example.com';

In Query 2, because the Secondary Index leaf node contains the email and the Primary Key (id), the Execution Engine never queries the Clustered Index. It extracts the id directly from the Secondary Index and returns. This eliminates 50% of the Disk I/O overhead. (In EXPLAIN, this appears as Using index).

Interview: What Happens Internally?

Reasoning Challenge

Scenario: You have a table with 10 million rows. You add a Secondary Index on a boolean column is_active. However, when you run EXPLAIN SELECT * FROM users WHERE is_active = 1;, the Optimizer chooses a Full Table Scan (ALL) instead of using your new index.

Question: Why did the Optimizer completely ignore your index?

View the Internal Explanation

The Optimizer ignored the index due to Low Selectivity (Low Cardinality) combined with the cost of the Double Lookup.

Because is_active is a boolean, assume 80% of your users are active. If the Optimizer used the index, it would have to find 8 million is_active=1 entries in the Secondary Index, and then perform 8 million separate B+Tree traverses into the Clustered Index to retrieve the SELECT * data.

Because secondary index lookups cause Random Disk I/O, executing 8 million random lookups would be catastrophic for the physical disk and the Buffer Pool. The Optimizer's cost-model correctly calculated that ignoring the index and simply reading the Clustered Index sequentially from start to finish (a Full Table Scan using Sequential Disk I/O) is drastically cheaper and faster.
