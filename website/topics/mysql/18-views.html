18. Views & Execution Algorithms

Admin & Internals

Views

A View is a virtual table defined by a SQL query. It contains no physical data on disk (unless it is a Materialized View, which MySQL does not natively support without workarounds). When you query a View, the MySQL Optimizer must determine how to extract the data from the underlying physical tables.

The Optimizer Algorithms: MERGE vs TEMPTABLE

When creating a View, MySQL uses one of two internal execution strategies.

1. The MERGE Algorithm

CREATE ALGORITHM=MERGE VIEW active_users AS 
SELECT id, email FROM users WHERE status = 'Active';

-- Your Query
SELECT * FROM active_users WHERE id = 105;

Execution: The MySQL Parser intercepts your query, retrieves the View definition from the Data Dictionary, and literally merges the two statements together before passing it to the Optimizer: SELECT id, email FROM users WHERE status = 'Active' AND id = 105;. This is extremely fast because the Optimizer can use the underlying Primary Key index.

2. The TEMPTABLE Algorithm

CREATE ALGORITHM=TEMPTABLE VIEW department_headcount AS 
SELECT department_id, COUNT(*) as total FROM employees GROUP BY department_id;

Execution: Because the View contains aggregation (GROUP BY), MySQL cannot simply merge a WHERE clause into it. When you query this View, the Execution Engine creates an internal temporary table, executes the entire View definition to populate it, and then runs your outer query against the temporary table. This is significantly slower.

Updatable vs Non-Updatable Views

Can you run an UPDATE or INSERT statement against a View?

  • Updatable: If the View maps 1-to-1 to the underlying physical table (using the MERGE algorithm, no aggregates, no DISTINCT, no UNION), MySQL translates your UPDATE active_users into an UPDATE users affecting the Buffer Pool.
  • Non-Updatable: If the View uses the TEMPTABLE algorithm (aggregates, grouping), it is strictly read-only. Modifying an average or a count has no logical reverse-mapping to the physical rows.
