6. Aggregate Functions & Execution

MySQL Engine Internals & Querying

Aggregate Functions

Aggregate functions (COUNT, SUM, AVG, MIN, MAX) perform calculations on a set of values and return a single scalar value. While the SQL syntax is straightforward, the Optimizer and Storage Engine interaction can vary drastically based on indexes and the presence of NULL values.

COUNT(*) vs COUNT(column) Internals

A fundamental edge case in SQL is how the Execution Engine treats NULL during aggregation.

Syntax Semantic Behavior Optimizer Execution Strategy
COUNT(*) Counts every row in the result set, including rows with NULLs. In InnoDB, exact row counts are not stored globally due to MVCC (concurrent transactions see different row counts). The Optimizer picks the smallest secondary index available and performs a fast index scan to count rows, avoiding reading physical table data.
COUNT(col) Counts only rows where col is NOT NULL. The Execution Engine must evaluate the column data for every row. If col is indexed, it scans the index. If not, it forces a Full Table Scan to check each row for NULL.
Edge Case: Empty Sets and NULL

What happens when an aggregate function runs against an empty result set?

  • COUNT(*) returns 0.
  • SUM(price), AVG(price), MIN(price), and MAX(price) return NULL.

If your application expects a numeric value, SUM() returning NULL can cause crashes. You must wrap it: IFNULL(SUM(price), 0).

MIN/MAX Optimization (Select Tables Optimized Away)

When you query SELECT MIN(id) FROM users; on an indexed column, the MySQL Optimizer applies a highly specific optimization shortcut.

Because B+Tree indexes are already sorted mathematically:

  • To find MIN(id), the Storage Engine simply traverses down the left-most edge of the B+Tree to the very first leaf node. It reads one value and stops.
  • To find MAX(id), it traverses down the right-most edge to the very last leaf node.

If you run EXPLAIN SELECT MIN(id) FROM users;, the Extra column will say "Select tables optimized away". This means the Execution Engine didn't even bother reading rows; the Optimizer extracted the answer directly from the B+Tree structure in O(log N) time.

Interview: What Happens Internally?

Reasoning Challenge

Query:

SELECT COUNT(status) FROM orders;

Question: The table orders has 1,000,000 rows. You notice this query is extremely slow, taking multiple seconds. However, SELECT COUNT(*) FROM orders; takes 0.05 seconds. Explain why this happens internally and how COUNT(*) achieves such speed.

View the Internal Explanation

Because COUNT(status) requires verifying that status IS NOT NULL for every single row, the Execution Engine must evaluate the status column. If status is not indexed, InnoDB must load 1,000,000 physical data pages from disk into the Buffer Pool (a Full Table Scan) just to check the nullability.

Conversely, COUNT(*) simply counts the presence of rows. The MySQL Optimizer knows it doesn't need to read the physical table data. It looks at the Data Dictionary, finds the smallest Secondary Index on the table (for example, an index on created_at), and simply scans the leaf nodes of that tiny index in memory. It counts the entries in the index and returns the result, completely bypassing the massive physical table scan.
