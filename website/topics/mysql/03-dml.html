3. DML & Buffer Pool Interaction

MySQL Engine Internals & Querying

DML (INSERT, UPDATE, DELETE)

Data Manipulation Language (DML) is responsible for modifying row data. However, understanding DML requires distinguishing between universal SQL Standard definitions and the physical InnoDB Storage Engine implementation.

SQL Layer vs InnoDB Layer

At the SQL Standard level, an UPDATE simply changes a value. But at the InnoDB Storage Engine level, data files on disk are almost never updated immediately. Instead, InnoDB performs modifications in memory (the Buffer Pool) and relies on transaction logs to guarantee durability.

The InnoDB Buffer Pool: The Heart of DML

InnoDB caches table data and indexes in a memory area called the Buffer Pool. When you execute a DML statement, MySQL does not immediately write the changes to the physical .ibd file on disk. Doing so would cause catastrophic random I/O bottlenecks.

What happens internally during an UPDATE?

UPDATE users SET status = 'Active' WHERE id = 105;
  1. Parser & Optimizer: The MySQL Server parses the query and the Optimizer decides to use the Primary Key index to find id = 105.
  2. Buffer Pool Check: The Execution Engine asks InnoDB for the row. InnoDB checks if the 16KB page containing id = 105 is currently in the Buffer Pool (RAM).
  3. Disk Read (if necessary): If the page is not in memory, InnoDB reads it from the physical disk into the Buffer Pool.
  4. Undo Log Generation (MVCC): InnoDB writes a copy of the old row data (e.g., status = 'Inactive') to the Undo Log. This ensures that if you issue a ROLLBACK, or if another transaction needs to see the previous state (Consistent Read), the old data is available.
  5. Page Modification: InnoDB updates the row in memory inside the Buffer Pool. The page is now marked as dirty (meaning it differs from what is currently on disk).
  6. Redo Log Generation: InnoDB writes the physical change to the Redo Log Buffer. Upon COMMIT, this buffer is flushed to the physical Redo Log file on disk (Write-Ahead Logging). This guarantees that even if the server crashes right now, the change survives.
  7. Checkpointing: Much later, a background thread asynchronously flushes the "dirty page" from the Buffer Pool to the physical .ibd data file.

DML Edge Cases & Concurrency

Edge Case: UPDATE with Implicit Type Conversion

If you run an UPDATE where the WHERE clause requires type conversion, the Optimizer might ignore your index, converting an instant primary-key lookup into a catastrophic Full Table Scan.

-- Assume 'phone_number' is a VARCHAR(20) with an index.
UPDATE users SET status = 'Verified' WHERE phone_number = 9876543210;

Because you provided a numeric literal instead of a string ('9876543210'), MySQL must cast every VARCHAR row to an integer to compare them. The index is ignored, and the entire table is locked (depending on isolation level) during the scan.

DELETE and Gap Locks

If you run a DELETE with a range condition (e.g., DELETE FROM orders WHERE status = 'Pending'), InnoDB does not just lock the rows it deletes. To ensure transaction isolation (preventing "Phantom Reads" in REPEATABLE READ), InnoDB places Gap Locks on the index ranges between the pending orders, preventing other transactions from inserting new 'Pending' orders until your transaction commits.

Interview: What Happens Internally?

Reasoning Challenge

Scenario: You run a massive DELETE FROM logs WHERE created_at < '2025-01-01'; that affects 10 million rows. It runs for 30 minutes, and then you press CTRL+C to cancel it.

Question: What happens to the database internally while it cancels? Why does the cancellation take a long time, and what logs are involved?

View the Internal Explanation

When you cancel a DML statement, MySQL must initiate a Rollback. Because InnoDB guarantees ACID compliance, it cannot leave the database in a partially deleted state.

  • During the 30 minutes the query was running, InnoDB was heavily writing the old row versions to the Undo Log.
  • When you cancel the query, InnoDB reads the Undo Log backwards and physically reconstructs the 10 million rows back into the Buffer Pool.
  • This process generates immense CPU usage and disk I/O, meaning the rollback might take just as long (or longer) than the original DELETE statement.
  • Meanwhile, the Redo Log continues logging the rollback modifications to ensure that if the server crashes during the rollback, crash recovery can resume the rollback process on startup.
