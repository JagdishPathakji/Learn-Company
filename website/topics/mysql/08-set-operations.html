8. Set Operations (UNION)

MySQL Engine Internals & Querying

Set Operations: UNION vs UNION ALL

Set operations combine the result sets of two or more SELECT queries. While the syntax is simple, the internal execution overhead between UNION and UNION ALL is one of the most common causes of CPU spikes in poorly written applications.

Internal Execution Differences

1. UNION ALL (Fast Append)

SELECT email FROM users
UNION ALL
SELECT email FROM archived_users;

Execution Path: The Execution Engine runs the first query and streams the rows directly to the client. It then runs the second query and appends the rows to the stream. There is virtually zero overhead. It simply concatenates the two streams.

2. UNION (Implicit DISTINCT)

SELECT email FROM users
UNION
SELECT email FROM archived_users;

Execution Path: A standard UNION mathematically requires uniqueness (removing duplicates). To achieve this, the Storage Engine cannot stream the results immediately.

  1. The Execution Engine runs both queries.
  2. It writes all results into an Internal Temporary Table.
  3. It builds a unique index on this temporary table to identify and discard duplicate rows.
  4. If the dataset is large, this temporary table exceeds memory limits and is written to physical disk.
  5. Finally, it reads the deduplicated data from the temporary table and streams it to the client.
Performance Edge Case

If you know mathematically that the two queries will never return overlapping duplicate rows (for example, Query A gets status='Active' and Query B gets status='Deleted'), writing UNION is a massive performance error. Always explicitly write UNION ALL unless you specifically require the database to spend CPU cycles deduplicating the results.

Interview: What Happens Internally?

Reasoning Challenge

Scenario: You execute a UNION between two massive tables containing 5 million rows each. The server CPU spikes to 100%, and the query takes 45 seconds. You change it to UNION ALL and it completes in 2 seconds.

Question: What physical disk and memory structures were heavily utilized during the 45-second query that were completely bypassed in the 2-second query?

View the Internal Explanation

During the UNION query, the MySQL Execution Engine had to create an Internal Temporary Table to deduplicate the 10 million combined rows. Because 10 million rows cannot fit in the standard in-memory tmp_table_size allocation, MySQL had to create an on-disk temporary table using the InnoDB storage engine.

It then had to insert all 10 million rows into this physical temp file and attempt to build a unique index on them to filter duplicates. This caused immense physical Disk I/O and CPU thrashing for sorting.

By changing to UNION ALL, you bypassed the temporary table and deduplication phase entirely. The Execution Engine simply executed the queries and flushed the network buffers directly to the client as the rows were read from the B+Tree, resulting in a 2-second execution.
