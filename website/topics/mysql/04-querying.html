4. DQL & Execution Sequence

MySQL Engine Internals & Querying

Data Query Language (DQL)

DQL consists almost entirely of the SELECT statement. However, writing a SELECT query and understanding how MySQL parses and executes it are completely different concepts.

The Logical Execution Sequence

At the SQL Standard level, queries are evaluated in a strict logical sequence. You type the query starting with SELECT, but the database evaluates SELECT almost at the very end.

  1. FROM / JOIN: Identify the source tables and merge them.
  2. WHERE: Filter the rows based on specific conditions.
  3. GROUP BY: Aggregate the remaining rows into buckets.
  4. HAVING: Filter the buckets (groups) created by GROUP BY.
  5. SELECT: Evaluate expressions, aliases, and select the final columns.
  6. DISTINCT: Remove duplicate rows.
  7. ORDER BY: Sort the final result set.
  8. LIMIT: Truncate the result set to a specific count.
MySQL Optimizer Deviation

While the logical sequence dictates how the query semantics behave (e.g., why you cannot use a SELECT alias in the WHERE clause), the MySQL Optimizer is free to alter the physical execution order if it guarantees the same final result. For example, the Optimizer might push a LIMIT operation down into the index scan to stop reading early, rather than waiting for step 8.

WHERE vs HAVING Internals

A senior developer must understand the physical consequence of placing a condition in WHERE versus HAVING.

-- Scenario A: Filtering in WHERE
SELECT department_id, COUNT(*) as emp_count 
FROM employees 
WHERE status = 'Active' 
GROUP BY department_id;

-- Scenario B: Filtering in HAVING (Anti-Pattern)
SELECT department_id, status, COUNT(*) as emp_count 
FROM employees 
GROUP BY department_id, status
HAVING status = 'Active';

Internal Execution Differences

  • WHERE: Filters rows before they enter the aggregation phase. MySQL can use an index on status to instantly fetch only active employees. The resulting dataset sent to the GROUP BY engine is very small.
  • HAVING: Filters rows after aggregation. In Scenario B, MySQL must read every single employee (Full Table Scan), group them all, calculate counts for both Active and Inactive employees into a temporary table, and then discard the Inactive rows. This causes massive memory waste and CPU overhead.

GROUP BY and ORDER BY: Filesort vs Index

When you ask MySQL to ORDER BY or GROUP BY, it must somehow organize the data. It has two choices:

  1. Use an Index: If the data is already stored in a B+Tree sorted by the requested column, MySQL just reads the index in order. This requires zero extra CPU effort.
  2. Using filesort: If no index matches the sort requirement, MySQL must fetch all the unsorted rows, place them into a memory buffer (the Sort Buffer), and run a QuickSort algorithm. If the data exceeds sort_buffer_size, MySQL writes temporary chunks to the physical disk, merging them later. This is extremely slow.

Interview: What Happens Internally?

Reasoning Challenge

Query:

SELECT total_price AS revenue 
FROM orders 
WHERE revenue > 1000;

Question: This query fails with an "Unknown column 'revenue' in 'where clause'" error. Why does MySQL throw this error, and at what layer does the failure occur?

View the Internal Explanation

The failure occurs in the MySQL Server Layer during the Preprocessor (Resolver) phase, before optimization or execution.

Because of the Logical Execution Sequence, MySQL resolves and validates the WHERE clause before it processes the SELECT clause. At the moment it is checking WHERE revenue > 1000, the alias revenue has not yet been defined by the SELECT clause. The preprocessor checks the data dictionary for a physical column named revenue in the orders table, fails to find it, and throws the error.
