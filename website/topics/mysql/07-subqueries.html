7. Subqueries & Materialization

MySQL Engine Internals & Querying

Subquery Execution & Optimizer Changes

A subquery is a query nested inside another query. While SQL allows you to place them in the SELECT, FROM, or WHERE clauses, how the MySQL Optimizer executes them depends heavily on whether they are Uncorrelated or Correlated, and what version of MySQL you are running.

Uncorrelated vs Correlated Execution

1. Uncorrelated (Independent) Subqueries

An uncorrelated subquery does not depend on data from the outer query. It can be executed entirely on its own.

SELECT * FROM employees 
WHERE department_id IN (SELECT id FROM departments WHERE name = 'Engineering');

Internal Execution: Historically, MySQL would execute the subquery once, generate a result list, and then scan the outer query. In modern MySQL (8.0+), the Optimizer often applies Semi-Join optimization, effectively rewriting this into a highly optimized JOIN internally.

2. Correlated Subqueries

A correlated subquery references a column from the outer query.

SELECT e1.name, e1.salary
FROM employees e1
WHERE e1.salary > (
    SELECT AVG(salary) 
    FROM employees e2 
    WHERE e2.department_id = e1.department_id
);

Internal Execution: Because the inner query relies on e1.department_id, it cannot be executed independently. The Execution Engine must evaluate the outer query row-by-row. For every row in e1, it passes the department_id into the inner query and executes it. If e1 has 10,000 rows, the subquery executes 10,000 times. This is classically a massive performance bottleneck.

Subquery Materialization (MySQL 8.x)

When dealing with subqueries in the FROM clause (often called Derived Tables), older versions of MySQL would physically execute them and write the results to an internal temporary table.

SELECT t.dept_id, t.total
FROM (SELECT department_id as dept_id, SUM(salary) as total FROM employees GROUP BY department_id) t
WHERE t.total > 500000;

Modern MySQL uses Subquery Materialization. The Optimizer evaluates the cost. If it's cheaper, it creates an in-memory temporary table, populates it with the subquery result, and builds an internal hash index on it instantly so the outer query can probe it quickly. If the result is too large for memory (exceeds tmp_table_size), it materializes it to disk.

Interview: What Happens Internally?

Reasoning Challenge

Query:

SELECT * FROM orders 
WHERE user_id IN (SELECT id FROM users WHERE status = 'Banned');

Question: In MySQL 5.5, this query was famously disastrous for performance, but in MySQL 8.0, it executes almost instantly. What internal change to the Optimizer caused this?

View the Internal Explanation

In older versions of MySQL, the Optimizer handled IN (subquery) very poorly. It would often rewrite it into a correlated EXISTS clause internally, forcing a full table scan of the orders table and evaluating the subquery for every single order.

In MySQL 8.0, the Optimizer introduced Semi-Join Transformations. When the Parser and Optimizer evaluate this query, they realize the subquery is independent. The Optimizer internally rewrites the execution plan to perform a Hash Join or Nested Loop Join between orders and users, stopping at the first match for each user (to prevent duplicating orders if the subquery returned multiple matching users). This completely eliminates the row-by-row subquery execution penalty.
