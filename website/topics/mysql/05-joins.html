5. JOINs & Optimizer Execution

MySQL Engine Internals & Querying

JOIN Fundamentals

At the SQL Standard level, JOINs mathematically represent Cartesian products combined with filtering criteria. However, at the MySQL Optimizer level, evaluating a JOIN involves selecting a physical execution algorithm and determining the optimal table order.

MySQL JOIN Algorithms (Version Aware)

MySQL does not evaluate JOINs simultaneously. It reads a row from the first table (the driving table), and then searches the second table (the driven table) for matches. This requires specific physical algorithms.

1. Nested-Loop Join (NLJ)

This is the standard execution path when the joining column on the second table has an index.

  • MySQL reads a row from Table A.
  • It performs a fast B+Tree lookup on Table B's index.
  • It repeats this for every row in Table A.

2. Block Nested-Loop (BNL) — Historical (Pre-8.0.18)

If Table B did not have an index, old versions of MySQL would read a chunk of Table A into a "Join Buffer", and then scan Table B entirely, comparing it against the buffer. This was notoriously slow for large tables.

3. Hash Join — Current MySQL 8.x Standard

Starting in MySQL 8.0.18, Hash Joins completely replaced Block Nested-Loop joins for non-indexed joins.

  • Build Phase: MySQL scans Table A (the smaller table) and builds an in-memory Hash Table using the join column as the hash key.
  • Probe Phase: MySQL scans Table B, hashes its join column, and instantly probes the in-memory Hash Table for matches.
  • Result: Massive performance improvements for analytical queries missing indexes.

INNER vs LEFT JOIN: Optimizer Freedom

The difference between INNER and LEFT join is not just semantic (whether unmatched rows are kept). It heavily restricts the MySQL Optimizer.

-- INNER JOIN
SELECT * FROM users u INNER JOIN orders o ON u.id = o.user_id;

For an INNER JOIN, the Optimizer is free to choose the Driving Table. It evaluates statistics. If orders is smaller or highly filtered by a WHERE clause, the Optimizer might execute orders -> users. It calculates the lowest cost.

-- LEFT JOIN
SELECT * FROM users u LEFT JOIN orders o ON u.id = o.user_id;

For a LEFT JOIN, the Optimizer is forced to use users as the driving table, because it must guarantee that every user is evaluated at least once, even if they have no orders. This restriction can sometimes lead to suboptimal execution plans if the driving table is massive.

Edge Case: ON vs WHERE in LEFT JOINs

A common failure point for developers is misunderstanding when filtering occurs in a LEFT JOIN.

Semantic & Execution Difference 
-- Case A: Filtering in ON
SELECT * FROM users u 
LEFT JOIN orders o ON u.id = o.user_id AND o.total > 500;

-- Case B: Filtering in WHERE
SELECT * FROM users u 
LEFT JOIN orders o ON u.id = o.user_id 
WHERE o.total > 500;
  • Case A: The condition o.total > 500 is evaluated during the join. If a user has an order with a total of 100, the join fails for that order, but the user is still returned in the final result set with NULLs for the order columns (because it is a LEFT JOIN).
  • Case B: The LEFT JOIN completes first, returning all users. Then, the WHERE clause runs. Because users without large orders will have o.total evaluated as NULL (or 100), the WHERE clause evaluates to FALSE, and those users are removed entirely. Case B effectively converts the LEFT JOIN into an INNER JOIN.

Interview: What Happens Internally?

Reasoning Challenge

Scenario: You join two tables: customers (10,000 rows) and transactions (5,000,000 rows). There is no index on the joining column. You are using MySQL 8.0.20.

Question: What physical execution strategy will MySQL use, and why is it faster than older versions of MySQL?

View the Internal Explanation

Because there is no index, MySQL 8.0.20 will utilize a Hash Join.

  1. The Optimizer determines customers is the smaller table.
  2. During the Build Phase, it scans the 10,000 customers and hashes the join column, placing it into the join_buffer_size memory area.
  3. During the Probe Phase, it scans the 5,000,000 transactions. For each transaction, it hashes the join column and does an O(1) memory lookup against the customer hash table.

This is drastically faster than older versions of MySQL (pre-8.0.18), which would have used Block Nested-Loop (BNL). BNL would load chunks of the customer table and force MySQL to scan the 5,000,000 transactions multiple times over, causing severe CPU and disk I/O thrashing.
