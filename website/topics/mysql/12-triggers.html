Trigger Execution & Internals

A Trigger is a named database object associated with a table that activates automatically in response to an INSERT, UPDATE, or DELETE.

BEFORE vs AFTER Triggers

The distinction between BEFORE and AFTER defines exactly when the Execution Engine fires the trigger relative to the InnoDB Buffer Pool modification.

Timing Internal Behavior Primary Use Case
BEFORE Fires before the row is modified in the Buffer Pool. The trigger can intercept and modify the NEW values before they are written to the page. Data validation, formatting, or dynamically calculating defaults.
AFTER Fires after the Buffer Pool page is modified, but before the transaction commits. Audit logging (writing to a separate table), because you know the original DML operation succeeded.

Triggers and Transaction Boundaries

The most important internal concept of a Trigger is that it executes within the same transaction as the statement that invoked it.

If you execute an UPDATE that fires an AFTER UPDATE trigger (which inserts a row into an audit table):

  • The original UPDATE generates Undo/Redo logs and modifies a page.
  • The Trigger's INSERT generates its own Undo/Redo logs and modifies a page.
  • If the Trigger fails (e.g., the audit table doesn't exist or violates a constraint), the entire transaction rolls back. The original UPDATE is undone via the Undo Log.
