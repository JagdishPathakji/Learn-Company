1. MySQL Introduction & Architecture

MySQL Engine Internals & Querying

High-Level MySQL Architecture

To truly understand how MySQL processes SQL, you must abandon the idea that MySQL is just a "black box" that accepts queries and returns data. MySQL uses a highly modular client-server architecture composed of three distinct layers.

Client Layer (Connection Handling, Authentication, Security) ↓ Server Layer (Parser, Preprocessor, Optimizer, Caches, Execution Engine) ↓ Pluggable Storage Engine Layer (InnoDB, MyISAM, Memory, etc.) ↓ File System (Data Files, Redo Logs, Undo Logs, Binlogs)
The "Pluggable" Storage Engine Concept

Unlike Oracle or SQL Server, MySQL separates query processing (Server Layer) from data storage (Storage Engine Layer). The Optimizer decides how to execute a query, but it must ask the Storage Engine via an API (the Handler API) to actually retrieve the rows. InnoDB is the default and only engine you should use for transactional workloads.

The Conceptual Query Execution Path

What happens internally when you press Execute in MySQL Workbench?

  1. Connection & Threading: The Client connects. MySQL assigns a dedicated thread to handle this connection.
  2. Parser: The SQL string is broken down into a "parse tree". Syntax errors are caught here.
  3. Preprocessor (Resolver): MySQL checks semantics. Do the tables exist? Do the columns exist? Does the user have privileges?
  4. Query Optimizer: This is the brain of MySQL. It calculates the cheapest "Execution Plan". Should it use an index? Should it do a full table scan? Which table should it join first? (Cost is calculated based on disk I/O and CPU predictions).
  5. Execution Engine: Follows the optimizer's plan and calls the Handler API to fetch rows from the Storage Engine.
  6. InnoDB Engine (Storage): Searches the Buffer Pool (Memory) for the requested data pages. If missing, it fetches them from the physical disk (.ibd files).

MySQL Workbench & Programming Guidelines

MySQL Workbench is merely a GUI client living in the "Client Layer". It does not execute queries—it sends TCP/IP packets containing SQL strings to the MySQL Server port (default 3306).

Common Misconception

Many beginners think Workbench is the database. If Workbench crashes, your database is fine. The MySQL Server daemon (mysqld) is a background service doing the actual work.

SQL Programming Guidelines

  • Keywords Uppercase, Identifiers Lowercase: SELECT id, name FROM users;
  • Use InnoDB: Always ensure ENGINE=InnoDB. (This is default in modern MySQL).
  • Explicit Joins: Never use comma-separated tables in the FROM clause. Always use INNER JOIN ... ON ....
  • Avoid SELECT *: It wastes memory in the Buffer Pool, increases network traffic, and prevents "Covering Index" optimizations (which we will cover in the Indexes chapter).

Interview: What Happens Internally?

Scenario

Query: SELECT * FROM users WHERE age > 20;

Question: Walk me through exactly what happens internally from the moment this query is submitted until the result is returned.

View the Internal Execution Path
  1. The client sends the SQL string via TCP/IP to the MySQL connection handler.
  2. The Parser checks for syntax validity (e.g., ensuring FROM and WHERE are spelled correctly) and builds a parse tree.
  3. The Preprocessor verifies that the users table and the age column actually exist in the data dictionary, and that the user has SELECT privileges.
  4. The Optimizer evaluates execution plans. It checks if there is an index on age. It estimates how many rows have age > 20 based on index statistics. If the number is very high (e.g., 80% of the table), the Optimizer might ignore the index entirely and decide a Full Table Scan is cheaper (to avoid random I/O).
  5. The Execution Engine asks InnoDB for the rows via the Handler API.
  6. InnoDB checks the Buffer Pool (RAM) for the pages containing these rows. If they aren't in memory, it reads them from the physical disk into the Buffer Pool.
  7. The rows are returned to the Execution Engine, which streams them back to the client.
