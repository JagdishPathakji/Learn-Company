Temporary Tables Internals

Temporary tables store transient data. However, there is a massive internal difference between a User-Created Temporary Table and an Internal Temporary Table generated by the MySQL Optimizer.

1. User-Created Temporary Tables

Created explicitly via CREATE TEMPORARY TABLE my_temp (...).

  • Scope: Bound strictly to the current client connection (Session). If User A creates a temp table, User B cannot see it. When the connection drops, the table is instantly dropped.
  • Storage: Stored in the ibtmp1 temporary tablespace (InnoDB) or in memory. They can have indexes, primary keys, and support transactions.
  • Use Case: Staging data during complex multi-step ETL procedures inside a stored procedure.

2. Internal Temporary Tables

Created automatically and silently by the MySQL Execution Engine when a query is too complex to stream directly to the client.

Common triggers for Internal Temp Tables:

  • UNION (without ALL).
  • GROUP BY and ORDER BY on different columns.
  • Derived tables / Subquery materialization.

Memory vs Disk Escalation

When the Optimizer decides to create an internal temp table, it first attempts to create it in RAM using the MEMORY storage engine. It is bounded by the tmp_table_size and max_heap_table_size configuration variables.

If the result set grows larger than these limits, or if it contains BLOB/TEXT columns (which the MEMORY engine historically could not handle), MySQL triggers a Disk Escalation. It pauses the query, converts the in-memory table to a physical on-disk InnoDB table, and continues. This transition causes a severe performance penalty.
