2. DDL & Schema Internals

MySQL Engine Internals & Querying

Data Definition Language (DDL)

DDL statements (CREATE, ALTER, DROP, TRUNCATE) define the structure of the database. Unlike DML (Insert/Update/Delete), DDL operations in MySQL historically caused locking issues, though modern MySQL has introduced Online DDL.

CREATE TABLE & File-Per-Table Internals

When you create a table, you aren't just defining rules; you are instructing the OS and the Storage Engine to allocate physical structures.

CREATE TABLE employees (
    emp_id INT AUTO_INCREMENT PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    hire_date DATE,
    department_id INT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

What happens internally during CREATE?

  • Data Dictionary Update: MySQL 8.0 uses a transactional data dictionary stored in InnoDB tables. It registers the table schema, columns, and types.
  • Physical File Creation: Assuming innodb_file_per_table=1 (default), InnoDB creates a physical file named employees.ibd on your hard drive.
  • Clustered Index Creation: InnoDB always organizes table data based on the Primary Key. The emp_id becomes the root of a B+Tree structure. The actual row data is physically stored in the leaf nodes of this B+Tree.
The Clustered Index Rule

If you don't define a PRIMARY KEY, InnoDB looks for a UNIQUE NOT NULL index to use as the clustered index. If neither exists, InnoDB silently generates a hidden 6-byte row ID column to cluster the data. Always define a Primary Key explicitly to avoid performance penalties.

ALTER TABLE & Online DDL

Modifying a table structure in production used to be a nightmare because it required a full table lock.

-- Adding a column
ALTER TABLE employees ADD COLUMN status VARCHAR(20) DEFAULT 'Active';

-- Changing a data type
ALTER TABLE employees MODIFY COLUMN first_name VARCHAR(100);

What happens internally during ALTER?

Modern MySQL uses Online DDL. Depending on the operation, InnoDB performs it in one of three ways:

  1. INSTANT: (MySQL 8.0+) Adding a column to the end of a table. It only updates the Data Dictionary metadata. It takes 0.01 seconds, even on a 500GB table! The physical rows aren't rewritten until they are updated later.
  2. INPLACE: Rebuilds the B+Tree structure in the background but allows concurrent INSERT/UPDATE/DELETE operations. An internal "Row Log" tracks ongoing changes and applies them at the end.
  3. COPY: (The worst case). MySQL creates a hidden temp table, copies every single row over, applies the change, drops the old table, and renames the new one. The table is locked for writes during this time. (Example: changing a column data type).
Edge Case: ALGORITHM Clause

To prevent accidental production outages, explicitly enforce the algorithm. If it requires a copy, the query will safely fail rather than locking production:

ALTER TABLE employees ADD COLUMN email VARCHAR(100), ALGORITHM=INSTANT;

DROP vs TRUNCATE Internals

Operation Internal Behavior Logging & Recovery
DELETE FROM table; Scans the B+Tree and marks every row as deleted. (DML) Generates massive Undo Logs and Redo Logs. Very slow. Can be rolled back.
TRUNCATE TABLE table; Drops the physical .ibd file and creates a brand new, empty one. (DDL) Does not log row deletions. Extremely fast. Cannot be rolled back. Reset AUTO_INCREMENT.
DROP TABLE table; Deletes the metadata from the Data Dictionary and deletes the physical .ibd file from disk. Releases all disk space back to the OS immediately.

Interview: What Happens Internally?

Scenario

Action: You run TRUNCATE TABLE audit_logs; on a 50GB table.

Question: Why is this instant, whereas DELETE FROM audit_logs; takes 20 minutes?

View the Internal Execution Path

DELETE is a DML operation. The Execution Engine must fetch every single page of the table into the Buffer Pool. For every row, it must:

  1. Write the old version of the row to the Undo Log (in case you ROLLBACK).
  2. Write the change to the Redo Log (for crash recovery).
  3. Mark the row as deleted in the data page (MVCC).

This generates immense CPU and disk I/O.


TRUNCATE is a DDL operation. The Storage Engine bypasses the Buffer Pool entirely. It simply goes to the operating system, deletes the physical audit_logs.ibd file, and instantly creates a new, empty audit_logs.ibd file. It does not generate row-level Undo or Redo logs.
