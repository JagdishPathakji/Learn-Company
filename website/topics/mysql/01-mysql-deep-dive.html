MySQL Deep Dive

InnoDB is the default, general-purpose storage engine for MySQL and MariaDB. While SQL defines how you write queries, the storage engine is the underlying software component that actually handles the physical storing, updating, and retrieving of data on the disk.InnoDB is famous because it is the engine that brings ACID compliance to MySQL.

UNDERSTANDING EXECUTION ORDER OF SQL QUERY

SQL we write :-
SELECT - FROM - JOIN - ON - WHERE - GROUP BY - HAVING - ORDER BY - LIMIT

Logical Meaning :-
FROM - JOIN - ON - WHERE - GROUP BY - HAVING - SELECT - ORDER BY - LIMIT

SQL USER DEFINED FUNCTION

A USER DEFINED function is a function that you create in the database to encapsulate reusable logic.

  1. Executes inside the database server
  2. Must return a value
  3. Can be used inside expressions such as SELECT, WHERE, etc
  4. RETURNS defines the return type; RETURN supplies the value
  5. DETERMINISTIC describes whether the same input reliably produces the same result
  6. Can read data, but stored functions have restrictions on modifying data and other operations (INSERT, UPDATE, DELETE not allowed)
  7. Functions called per row can become a major performance problem
  8. Function cannot return a TABLE
  9. NON DETERMINISTIS does not give same output for same input
  10. READS SQL DATA means function reads data from tables
  11. CONTAINS SQL means contains SQL statement
  12. NO SQL contains no SQL statement

SQL STORED PROCEDURE

  1. A stored procedure is a named program stored inside the MySQL database.
  2. CALL procedure_name(agruments)
  3. Paramaters :- IN (input only), OUT (output only), INOUT (input + output) [IN is the default if no mode is specified]
  4. IN Parameter
    • caller provides a value
    • procedure can read it
  5. OUT Parameter
    • Procedure puts a value into the parameter
    • Caller retrieves that value using a variable
  6. INOUT Parameter
    • Caller supplies initial value
    • Procedure can read and modify it
    • Modified value is available to the caller
  7. Procedure does not have RETURNS it can communicate results through:
    • SELECT (output multiple rows) and multiple SELECT allowed
    • OUT parameters
    • INOUT parameters
  8. Procedures can perform data modification (INSERT, UPDATE, DELETE)
  9. SIGNAL allows you to raise an error
  10. Procedure can call another procedure
  11. Procedure can call functions
  12. Functions cannot call procedure

Example:-

CREATE PROCEDURE sp_ArticleStats(
    IN articleId INT,
    OUT title VARCHAR(255),
    INOUT views INT
)
BEGIN
    -- IN: read the value supplied by caller
    SELECT article_title
    INTO title
    FROM articles
    WHERE article_id = articleId;

    -- INOUT: read the supplied value and modify it
    SET views = views + 1;
END;

SET @views = 10;

CALL sp_ArticleStats(
    101,       -- IN
    @title,    -- OUT
    @views     -- INOUT
);

SELECT @title, @views;

INDEXING

  1. Without an index, MySQL scan entire table until required row is found (O(n))
  2. An index is a separate data structure maintained by the database to locate rows efficiently
  3. MySQL storage engine, indexes are based on B-tree/B+tree structure
  4. PRIMARY KEY -- MySQL engine creates a Clustered index on PRIMARY KEY. The leaf pages of the clustered index contain the actual table row data. It is called clustered because table's actual records are organized (according to the primary key).
             Primary Index
                  │
             [B+Tree nodes]
                  │
        ┌─────────┴─────────┐
        ↓  	                 ↓
      leaf page            leaf page
   ┌─────────────┐       ┌─────────────┐
   │ id=1           │       │ id=500         │
   │ name=...       │       │ name=...       │
   │ other data     │       │ other data     │
   └─────────────┘       └─────────────┘
  1. If there is no primary key, MySQL engine still needs clustered index. It chooses this order:
    • PRIMARY KEY
    • first suitable UNIQUE NOT NULL index
    • Internal hidden 6-byte row ID
  2. UNIQUE KEY -- If table has both PRIMARY KEY and UNIQUE KEY, The UNIQUE KEY does not form clustered index. It forms secondary index which stores the primary key.

Example:-

email                         primary key
------------------------------------------------
a@example.com                 → 17
jagdish@example.com           → 42
rahul@example.com             → 73

When we search by email :- use email index to find email -> get primary key -> search clustered index using primary key -> retrives actual row

  1. COMPOSITE KEY -- There is one index containing two columns. [also mapped with primary key same as normal indexing]
    Consider:- (author_id, status_id)
    Conceptually index is sorted by author_id first and status_id as second.

    This COMPOSITE INDEXING works on search by
    • author_id
    • author_id and status_id
    but does not work for
    • status_id only
    because indexing is sorted based on author_id first which helps in B-Tree traversal while searching
  2. COMPOSITE PRIMARY KEY -- PRIMARY KEY(article_id, version_number)
    Now the clustered index is order by:- article_id first and version_number as second.
  3. FULLTEXT INDEX --
    MySQL builds table like this: 
    Word          → Articles containing it
────────────────────────────────────
mysql         → 101, 105, 120
database      → 101, 102, 120
index         → 102, 105
csharp        → 101, 110

TRANSCATION MANAGEMENT

PART 1 -- TRANSACTION BASICS

1. What is a transaction ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-
A transaction is a group of database operations that MySQL treats as one unit of work.

Example:

START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE account_id = 2;

COMMIT;

The two UPDATEs together represent one logical operation.

2. AutoCommit
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-
By default, MySQL normally operates with autocommit = 1.
Each individual statement is automatically committed when it successfully finishes.
Inside a transaction, autocommit is always false.

3. START TRANSACTION
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-
Start an explicit transaction. The following operations belong to this transaction until it ends.

4. COMMIT
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-
COMMIT tells MySQL that the transaction has successfully completed and its changes should be permanently accepted. Transaction locks are released.

5. ROLLBACK
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-
Abandon the transaction's changes and return the database to the appropriate state before that transaction's changes. Transaction locks are released.

6. What if one statement in TRANSACTION fails ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-
A statement error does not automatically mean the entire transaction has been rolled back. We decide whether to ROLLBACK or COMMIT in such scenarios.

7. Scenario Typical view
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-

                     START
                       │
                       ↓
                     ACTIVE
                       │
          ┌────────────────────┐
          │                         │
      operations              operations
          │                        │
          └─────────┬──────────┘
                      │
             ┌──────┴──────┐
             │                │
          COMMIT           ROLLBACK
             │                │
             ↓                ↓
         COMMITTED         ABORTED
             │                │
             └──────┬──────┘
                      ↓
                     END

PART 2 -- WHAT HAPPENS INSIDE InnoDB

  1. Client sends UPDATE to MySQL.
  2. MySQL parses the SQL.
  3. MySQL validates table, columns, syntax, permissions, etc.
  4. Optimizer decides how to find the target row, usually using an index if available.
  5. MySQL passes the storage work to InnoDB.
  6. InnoDB locates the page containing the target record.
    -- If the page is already in the Buffer Pool, InnoDB uses it from memory.
    -- If the page is not in the Buffer Pool, InnoDB reads that page from disk into the Buffer Pool.
  7. InnoDB finds the target record inside that page.
  8. InnoDB performs the transactional work required for the change:
    -- acquires required locks
    -- creates undo information
    -- creates redo information
  9. InnoDB modifies the record in the Buffer Pool.
  10. The modified page becomes a dirty page. [disk and buffer has different data]
  11. The transaction remains active until COMMIT or ROLLBACK.
    -- On COMMIT:
    i. transaction is finalized
    ii. required redo durability is handled
    iii. transaction becomes committed
    iv. transaction locks are released
    v. dirty pages do not necessarily need to be written to the data file immediately
    vi. Later, dirty pages are flushed from the Buffer Pool to disk.
    -- On ROLLBACK instead:
    i. InnoDB uses undo information to reverse the transaction's changes
    ii. transaction ends
    iii. transaction locks are released.

PART 3 -- UNDO LOG

Consider a transaction with UPDATE queries. After some query, we do ROLLBACK due to some reasons. So InnoDB needs to restore and preserve information about the previous state. That is the basic purpose of Undo.

"Undo records contain information that allows InnoDB to reverse transaction changes and importantly help reconstruct older row versions"

Undo is not simply a backup copy of the entire row. Instead, InnoDB maintains undo records describing transactional changes. During ROLLBACK, use undo information and restore previous state. InnoDB does not delete the undo information immediately after COMMIT.

Why can't InnoDB delete undo immediately after COMMIT ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
Because an older transaction may still need it.

T1                         T2
│                          │
│                          START
│                          │
│ UPDATE 10000 → 7000      │
│                          │
│ COMMIT                   │
│                          │
│                          │ SELECT
│                          │
│                          ↓
│                    may need older version

If T2's consistent read requires the older version, InnoDB may need Undo information to reconstruct it. Undo details are eventually purged.

Purge
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
Eventually, when old Undo information is no longer required by any transaction, InnoDB can clean it up. This process is called purging.
Long-running transactions can cause Undo/history to grow and can delay purge.


PART 3 -- REDO LOG + WAL

When we update some value using transaction, InnoDB modifies the page in memory. (initial balance = 10000)
-- Buffer Pool : balance = 9000
-- Disk : balance = 10000
The buffer pool page is now dirty.

What happens if the server suddenly crashes before that dirty page gets written to disk (RAM is lost as server crash) ? If we have no recovery mechanism, 9000 is LOST forever and disk still contains 10000. So we need a mechanism that records enough information to reconstruct the changes. That is the purpose of the REDO LOG.

"The REDO LOG records information about the changes made to InnoDB data pages so those changes can be reapplied during crash recovery."

Data Change --> REDO LOG --> "this changes needs to be reproducible".
The Redo Log contains information sufficient for InnoDB to redo the required page modification.

Why not just write the data page immediately ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
Suppose every update did:
1. UPDATE
2. Modify Buffer Pool
3. Write entire page to disk immediately (one page contain many records, while we may work only with one of them)
Thus, Redo provides a much more efficient recovery mechanism.

The Buffer Pool is where InnoDB works with pages.
The Redo Log provides the information required to recover page modifications.

What happens during UPDATE ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
1. Find the page
2. Page enters the buffer pool
3. Generate Redo information
4. Modify buffer pool page
5. Page becomes dirty

Why is Redo called "Redo" ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
"This change has been recorded, but the corresponding data page may not have reached disk. Apply the change again."

WAL (Write-Ahead Logging)
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
Redo Log introduced the concept of WAL.

Before a modified data page is written to disk, its corresponding log record must already be safely stored.
1. A transaction changes some data in memory.
2. The database creates a log record describing that change.
3. The log record is persisted safely.
4. Only then can the modified data page be written to disk.
The log goes ahead of the data page.

-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
COMMIT does not mean data page immediately written
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x

What if crash happens BEFORE COMMIT?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
It determines which transaction changes need to be recovered and which uncommitted work must ultimately be undone.
1. redo required page changes
2. undo changes belonging to uncommitted transactions
This is where Redo and Undo work together.

What if crash happens AFTER COMMIT?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x-x
Recovery sees the durable redo information and knows the committed change needs to be reflected in the database state.

Log Sequence Number
-x-x-x-x-x-x-x-x-x-x-x
A Log Sequence Number identifies the position of redo information in the redo log stream.

Redo Log
LSN 100 → change A
LSN 120 → change B
LSN 145 → change C
LSN 170 → change D

Pages also contain information related to the latest redo position reflected in them.

Page 42
page LSN = 145

During recovery, InnoDB can determine which redo records need to be applied to a page.

For example:
Page LSN = 145

Redo:
LSN 100
LSN 120
LSN 145
LSN 170
LSN 190

The page already reflects changes through 145.
So recovery can apply the relevant later changes:
170
190

Checkpoints
-x-x-x-x-x-x-x-x-x-x
Imagine server has been running for days. Redo logs become very large. We dont need to keep every redo record forever. Eventually InnoDB flushes dirty pages to disk and establishes a `checkpoint` representing how far recovery-relevant changes have been persisted. The logs before that checkpoint are no longer needed.

Redo vs Buffer Pool
-x-x-x-x-x-x-x-x-x-x-x-x
Buffer Pool : contains database pages and allows InnoDB to work efficiently in memory.
Redo Log : contains information about modifications needed for recovery.

PART 5 -- ACID

Atomicity ("All or Nothing")
Consistency (bring the database from one valid state to another)
Isolation (concurrently running transactions do not interfere with one another)
Durability (guarantees that once a transaction is committed, its changes are permanently saved)


PART 6 -- LOCKS

Suppose two transactions modify the same row. Without concurrency control, both could modify the same data unpredictably. So InnoDB uses locks to control conflicting operations.

When T1 modifies the row, X LOCK is acquired. If T2 tries to update, it has to WAIT until T1 commits and releases LOCK.

InnoDB can lock records/index entries and ranges of index entries, not just entire tables. This provides better concurrency as other transaction can work on different rows at same time.

Two basic lock types
---------------------
1. Shared Lock - S
Used when a transaction wants to read. Multiple transactions can generally hold compatible shared locks simultaneously.

2. Exclusive - X
Used when a transaction needs to modify a record. Only one transaction at a time can hold X LOCK on same resource.

COMMIT or ROLLBACK releases the transaction locks.


PART 7 -- MVCC Basics

MVCC
- MVCC = Multi-Version Concurrency Control.
- Purpose: allow transactions to read appropriate versions of rows while other transactions are modifying them.
- InnoDB uses Undo information to reconstruct older row versions.

Example:
Current row = 9000
Undo history → previous version = 10000

If T1 changes:
10000 → 9000

- T1 works with the current version, while another transaction may be able to read the older committed version depending on its read view/isolation level.

- Old versions are not permanent copies of the table.
- Old versions can eventually be removed by purge when no transaction needs them anymore.

NORMAL SELECT VS LOCKING SELECT
- NORMAL SELECT uses NO LOCK
- SELECT ... FOR UPDATE uses X Lock
- SELECT ... FOR SHARE uses S lock


PART 8 -- BINARY LOGS

Binlog and Redo Log solve different problems.

Why do we need Binlog ?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x
We have Redo Log :- Update -> REDO LOG -> Crash Recovery
Redo Log is an Inno DB storage-engine recovery mechanism.

MySQL also needs a log that records database changes at the server level specially for:
- replication
- point-in-time recovery

What does Binlog contain?
-x-x-x-x-x-x-x-x-x-x-x-x-x-x
The binlog records changes/events associated with transactions.

Redo vs Binglog
-x-x-x-x-x-x-x-x-x
Redo Log :-
= Belongs primarily to InnoDB
= Crash Recovery is main purpose
= Storage engine recovery log
= Used by InnoDB
= Information needed to recover page
= Not used for replication

Binlog :-
= Belongs primarily to MySQL server
= Replication and Recovery are main purpose
= Event oriented log
= Used by replicas and recovery tools
= Information related to transaction changes / events
= Used for replication

                    UPDATE
                      │
          ┌─────────┴─────────┐
          ↓         	           ↓
       REDO LOG                 BINLOG
          ↓                        ↓
   InnoDB recovery       	Replication
                         
Redo:
"information needed by InnoDB to recover pages" (so cant used by replicas)

Binlog:
"information about database changes/events that can be reproduced"
(Point in time recovery is major usage)

PART 9 -- FINAL CONLCUSION AND OVERVIEW

UNDO LOG :-
1. InnoDB transactional history used to reverse changes and reconstruct older row versions.
2. Answers "How do i go backward?".
3. Primary purpose to handle ROLLBACK.
4. Belongs to InnoDB
5. Backward direction (reconstruct / previous state).
6. Generated when InnoDB performs changes.
7. Stores info that help reconstruct the value.
8. Exists during the transaction. After commit, it maybe still needed temporarily by MVCC.
9. ROLLBACK is primary use.
10. Also used by ROLLBACK TO SAVEPOINT.
11. Used for crash recovery to undo incomplete / uncommitted transactional work after redo recovery.
12. Not used for point-in-time recovery.
13. Through InnoDB's purge process when no active transaction needs the old history, undo logs are cleared eventually.

-- What they actually store ?
1. transaction ID
2. undo record metadata
3. affected record information
4. undo record pointer (link to previous versions)
5. For an INSERT:
- Information needed to remove the inserted record during rollback.
For an UPDATE:
- Previous values of the columns that were changed.
For a DELETE:
- Information needed to reconstruct the deleted record.
For MVCC:
- The information required to reconstruct an older visible version of the row.

REDO LOG :-
1. InnoDB recovery log used to reapply/recover changes that may not have reached the data pages on disk before a crash.
2. Answers "How do I recover/reapply the change?"
3. Primary purpose is crash recovery and durability of InnoDB page changes.
4. Belongs to InnoDB.
5. Forward direction — reconstruct/reapply the required change.
5. Generated when InnoDB modifies database/index pages.
6. Stores information needed to reproduce the modifications to InnoDB pages during recovery.
7. Exists as part of the ongoing redo stream; after commit, the relevant redo must remain available until it is no longer needed for recovery, after which its space can be reused.
8. Crash recovery is the primary use.
9. Not used to perform normal ROLLBACK or ROLLBACK TO SAVEPOINT; rollback is primarily handled using Undo.
10. During crash recovery, Redo is used to reapply required changes, including changes whose dirty data pages had not yet been persisted to disk.
11. Not used for reconstructing old row versions.
12. Not used as the replication log.
13. Supports the WAL (Write-Ahead Logging) -- principle: required redo information must be persisted ahead of the corresponding data-page persistence so recovery remains possible.
14. Works with dirty pages in the Buffer Pool; a dirty page can remain in memory while its redo information provides crash-recovery protection.
15. COMMIT does not mean the data page is immediately written to disk; the committed transaction's required redo durability can be established while the dirty page is flushed later.
16. During crash recovery, InnoDB uses LSNs (Log Sequence Numbers) to determine which redo records are relevant to pages.
17. Through checkpointing, once older redo is no longer required for recovery, its space can eventually be reused.

-- What they actually store ?
1. Log sequence number
2. Information identifying the affected InnoDB page/structure.
3. Type of modification/operation performed.
4. Information needed to reproduce that modification during crash recovery.
5. For an INSERT:
- Information needed to reproduce the relevant page/index modification.
For an UPDATE:
- Information needed to reproduce the modification made to the affected InnoDB page.
For a DELETE:
- Information needed to reproduce the deletion-related page/index modification.

BINARY LOG (BINLOG)
1. MySQL server-level change/event log used to record transactions/events for replication and recovery workflows.
2. Answers "What database changes/events happened?"
3. Primary purpose is replication and point-in-time recovery (PITR).
4. Belongs to the MySQL server layer, rather than being an InnoDB-only log.
5. Generated when MySQL processes changes that are configured to be written to the binary log, such as INSERT, UPDATE, and DELETE.
6. Stores transaction/event information according to the configured binlog format:
STATEMENT → SQL statements
ROW → row changes
MIXED → combination depending on the situation
7. Exists independently of the InnoDB Undo/Redo logs; committed transaction events remain available according to binlog retention/expiration settings.
8. Replication is a primary use.
9. Also used for Point-in-Time Recovery (PITR) by replaying binlog events after restoring a backup.
10. Not used for normal ROLLBACK.
11. Not used for ROLLBACK TO SAVEPOINT.
12. Not used for MVCC or reconstructing old row versions.
13. Not used as the mechanism that directly recovers dirty InnoDB pages after a crash; that is the job of Redo.
14. A transaction that is rolled back is not treated as a successfully committed transaction for replication.
15. A transaction's binlog events are associated with the transaction and are finalized as part of the commit process.
16. Works with Redo Log during transaction commit; MySQL coordinates the storage engine and binary log so their transaction states remain consistent.
17. Can be used to restore a database from a backup and replay changes up to a specific time.
18. Binlog files can eventually be expired/purged when they are no longer required by replication or recovery.
19. Does not replace Undo or Redo; it solves a different problem.

-- What they actually store ?
1. Binlog event metadata
2. Transaction / event information
3. Information identifying the database/table involved in the event, where applicable.
4. The actual change information depends on the binlog format.
5. STATEMENT format: Stores the SQL statement that caused the change.
6. ROW format : Stores row-change events rather than simply storing the SQL statement.
7. Binlog also contains transaction boundary information, allowing a transaction's events to be represented as a transaction.
