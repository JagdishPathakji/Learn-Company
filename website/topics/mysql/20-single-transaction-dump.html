20. Single-Transaction Dump (MVCC Deep Dive)

Admin & Internals

The --single-transaction Flag

This is arguably the most critical backup concept for an InnoDB database. When generating a Logical Backup (e.g., using Workbench or mysqldump) on a live, active production database, you face a massive problem: Data Consistency.

The Consistency Problem

Imagine your backup takes 30 minutes to complete. It dumps the users table at 12:00, and the orders table at 12:30. What happens if a customer registers and places an order at 12:15?

  • The customer is NOT in the users backup (dumped at 12:00).
  • The order IS in the orders backup (dumped at 12:30).

When you restore this backup, you will have an orphaned order pointing to a non-existent user. Your database is mathematically corrupted.

The Solution: MVCC & Undo Logs

To fix this, you must run your backup with the --single-transaction flag. This instructs mysqldump to issue a START TRANSACTION WITH CONSISTENT SNAPSHOT command to the server before it reads any data.

What happens internally?

  1. The backup session initiates a transaction with the REPEATABLE READ isolation level.
  2. InnoDB notes the current System Version Number (Transaction ID).
  3. As the backup slowly scans the tables over 30 minutes, concurrent users continue to run UPDATE, INSERT, and DELETE.
  4. When a concurrent user modifies a row, InnoDB writes the old version of that row to the Undo Log.
  5. When the backup process reaches a row that was modified after the backup started, InnoDB's MVCC (Multi-Version Concurrency Control) engine recognizes the version mismatch.
  6. The backup process silently reads the old row data from the Undo Log, ignoring the newly committed data in the Buffer Pool.

Result: The backup receives a mathematically perfect freeze-frame of the entire database exactly as it looked at 12:00, without ever locking the database or preventing live customers from writing data.

Limitations and Edge Cases

DDL Breaks Snapshots

The --single-transaction flag only protects DML (Inserts/Updates/Deletes). If a DBA runs an ALTER TABLE or DROP TABLE while the backup is running, the physical schema changes. The backup will crash with a "Table definition has changed" error.

The Undo Log Purge Problem

Because the backup transaction remains open for 30 minutes, the InnoDB Purge Thread cannot delete any Undo Logs generated during that time. If your database experiences massive write volume during the backup, the Undo Log (stored in the system tablespace) will grow enormously, consuming physical disk space until the backup completes and commits.

Comparison: --lock-tables vs --single-transaction

  • --single-transaction: Used exclusively for transactional engines (InnoDB). Zero downtime.
  • --lock-tables: Used for non-transactional engines (MyISAM) which do not support MVCC. It physically locks every table for reading. The database is frozen and effectively offline for writes until the backup completes. Never use this for InnoDB.
